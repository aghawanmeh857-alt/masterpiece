# قاعدة بيانات Masterpiece

قاعدة مستقلة لـ **SQL Server**، خاصة بمنصة سعي. لم يُضف أي اتصال أو Backend إلى الموقع.

## أين توجد على جهازك؟

- اسم السيرفر: `localhost`
- نوع الدخول: **Windows Authentication**
- اسم القاعدة: **Masterpiece**

افتح SQL Server Management Studio (SSMS)، واتصل بالسيرفر أعلاه، ثم افتح **Databases** واضغط **Refresh**.

> نُقلت نفس القاعدة من LocalDB إلى `localhost` بواسطة Backup/Restore. النسخة المعتمدة الآن على `localhost`، ولا تحتاج تشغيل الموقع لرؤيتها. بقيت النسخة الأصلية على LocalDB احتياطًا.

## الملفات بالترتيب

| الملف | وظيفته |
|---|---|
| `001_create_database.sql` | إنشاء Masterpiece إذا لم تكن موجودة |
| `002_schema.sql` | الجداول الأساسية والمفاتيح والعلاقات والقيود |
| `003_views.sql` | استعلامات محفوظة لقراءة المحتوى والنشاط والتقدم ومجاميع الطلبات |
| `004_reference_data.sql` | الأدوار والتصنيفات والعملات والمهارات |
| `005_learning_and_meetings.sql` | اختبارات الدورات وغرف المقابلات |
| `006_demo_data.sql` | أمثلة اختيارية فقط؛ لا تُشغّل ضمن التثبيت الافتراضي |
| `007_example_queries.sql` | أمثلة سهلة لاستعراض الجداول والعلاقات وبيانات المستخدم |
| `tables.md` | شرح مبسط للجداول |
| `relationships.md` | مخططات العلاقات |

الجداول مكتوبة بأوامر `CREATE TABLE` و`PRIMARY KEY` و`FOREIGN KEY` و`UNIQUE` و`CHECK`. لا توجد إجراءات مخزنة أو تريغرز. لا تحتوي الملفات على أوامر حذف قاعدة بيانات أو حذف الجداول.

## التثبيت على جهاز آخر

داخل SSMS، افتح الملفات من 001 إلى 005 ونفّذها بالترتيب. افتحها بترميز UTF-8 للحفاظ على النصوص العربية.

أو من PowerShell في مجلد المشروع:

```powershell
.\database\Masterpiece\Install.ps1
```

لاختيار مثيل SQL Server مختلف:

```powershell
.\database\Masterpiece\Install.ps1 -Server '.\SQLEXPRESS'
```

التثبيت الافتراضي لا ينشئ مستخدمين أو شركات أو طلبات أو بيانات دفع. إعادة تشغيل الملفات لا تعيد إنشاء الجداول المثبتة. التعديلات المستقبلية على الجداول تحتاج سكربت ترقية جديد؛ لا يكفي تعديل ملف 002 وإعادة تشغيله.

## البيانات التجريبية الاختيارية

لتعبئة أمثلة بعد التثبيت، نفّذ `006_demo_data.sql`، أو:

```powershell
.\database\Masterpiece\Install.ps1 -DemoData
```

هذه أمثلة وهمية بدومين `.example`، تشمل الأنواع الستة للمحتوى، والتقديم والتعلّم والاختبار والتسجيل والمحادثات والمقابلات. المستخدمون بلا كلمات مرور أو PasswordHash، فلا توجد بيانات دخول جاهزة. الدفع التجريبي مجرد سجل محلي بقيمة 25 USD، ولا يتصل بمزود دفع ولا يخصم أموالًا.

## أهم قرارات التصميم

- `Listings` يحتوي البيانات المشتركة للكاردات. لكل نوع جدول تفاصيل واحد؛ الربط بالمفتاح المركب يمنع إضافة تفاصيل دورة إلى سجل مشروع مثلًا. قد يبقى السجل مسودة دون تفاصيل أثناء تعبئة النموذج.
- `UserRoles` يدعم الأدوار: مستخدم، ممثل شركة، أدمن. و`CompanyMembers` يربط حساب ممثل الشركة بالشركة التي يديرها.
- `Favorites` مشترك لكل المحتوى. `CartItems` يسمح بالدورات والورش والفعاليات والتدريب فقط؛ الوظائف والمشاريع مرفوضة بقيد داخل القاعدة.
- `OrderItems` يسمح بالمحتوى القابل للشراء فقط: الدورات والورش والفعاليات. التدريب لا يدخل الدفع. يُحفظ عنوان العنصر وسعره وقت الطلب؛ لا يتغيران بتغيير السعر الحالي.
- `CourseEnrollments` للدورات، و`Registrations` للورش والفعاليات. الواجهة الحالية تعرض الورش ضمن الأكاديمية، ويُفصل نوعها إلى `workshop` عند الربط المستقبلي.
- لا توجد فرق مشاريع، أو باقة بروفايل مدفوعة، أو قسم Portfolio مستقل؛ لأنها أُلغيت. بقي رابط معرض الأعمال ضمن الملف الشخصي والتقديم.
- الملفات الفعلية خارج قاعدة البيانات؛ `Files` يحفظ الاسم والنوع والحجم و`StorageKey`. لا يُحفظ رابط Blob من المتصفح، ولا ملف PDF نفسه داخل حقل نصي.
- لكل محتوى صورة واحدة وملف تفاصيل PDF واحد اختياريان. ملفات التعليم والشهادات صور أو PDF. الحد الأقصى للملف 10 ميغابايت.
- التواريخ `datetime2` بالتوقيت العالمي UTC. حقول `TimeZoneId` توضّح طريقة العرض، والقيمة الافتراضية `Asia/Amman`.
- العملات USD وJOD كبداية، والأسعار `decimal(19,3)` لدعم أجزاء الدينار. الطلب الواحد بعملة واحدة.
- معظم الروابط تستخدم معرّفات رقمية. `PublicId` و`LegacyKey` موجودان لتسهيل الربط بالواجهات الحالية دون الاعتماد على ترتيب أرقام Identity.
- لا يوجد حذف تلقائي متسلسل. العلاقات تمنع حذف سجل له بيانات مرتبطة. تتوفر حقول تعطيل/أرشفة/حذف منطقي للبيانات المهمة.
- `rowversion` يساعد لاحقًا على منع تعارض تعديلات المستخدمين، ولا يعني تاريخًا أو وقتًا. حدّث `UpdatedAt` صراحة عند التعديل.
- تُمنع الرسائل من مستخدم غير مشارك بواسطة علاقة مركبة. `MeetingRooms` يحفظ معلومات المقابلة فقط، ولا ينشئ خدمة اتصال فيديو.

## عند إضافة Backend لاحقًا

هذه مسؤوليات واضحة للـBackend، لم نخفها داخل تريغرز معقدة:

1. التحقق من تسجيل الدخول والصلاحيات: الأدمن ينشر الدورات والورش والفعاليات، وممثل الشركة يدير وظائف وتدريبات شركته، وصاحب المشروع يدير مشروعه.
2. إنشاء المحتوى كمسودة، ثم إنشاء جدول التفاصيل، ثم النشر داخل معاملة واحدة. التحقق من اكتمال التفاصيل وعدم انتهاء موعد التقديم.
3. تأكيد الدفع من الخادم ومزود الدفع، ومطابقة السعر والعملة وصاحب الطلب، ثم إنشاء الالتحاق أو التسجيل. لا تعتمد على قيم أرسلها المتصفح.
4. منع تجاوز سعة الورش والفعاليات وعدد محاولات الاختبارات داخل معاملات مؤمنة ضد التزامن.
5. حساب إجابات الاختبارات ودرجاتها على الخادم، وعدم إرسال `IsCorrect` للطالب قبل إنهاء المحاولة.
6. كتابة سجل حالة التقديم و`AuditLogs` مع العملية الأصلية داخل نفس المعاملة.
7. التحقق من ملكية المرفقات ومحتواها الحقيقي وفحصها، وعدم إتاحة الملفات المرفوضة أو غير المفحوصة.
8. تخزين تجزئة آمنة لكلمة المرور فقط؛ لا تحفظ كلمة المرور أو بيانات البطاقات البنكية. `PasswordHash` الفارغ لا يسمح بتسجيل الدخول.

## الفحوصات

فحص ملفات التصميم فقط:

```powershell
node scripts/check-masterpiece-db.cjs
```

اختبار فعلي على SQL Server المحلي (شغّله قبل تعبئة البيانات التجريبية الاختيارية):

```powershell
node scripts/check-masterpiece-db.cjs --integration
```

كل بيانات الاختبار تُنشأ داخل معاملات ثم تُلغى بـ`ROLLBACK`، ولا تبقى حسابات أو عمليات شراء. أرقام Identity قد تتقدم بعد الاختبار؛ هذا طبيعي، ولا ينبغي افتراض أن أول مستخدم رقمه 1.

نجحت 15 حالة تكامل، تشمل السيناريو الكامل، ومنع تكرار البريد والتقديم والتسجيل والمفضلة، واستبعاد الوظائف والمشاريع من السلة، ومطابقة نوع المحتوى، ورفض الأسعار السالبة، وربط التقدم بالدورة الصحيحة، ومطابقة عملة الطلب، وصحة علاقات الرسائل والاختبارات.
